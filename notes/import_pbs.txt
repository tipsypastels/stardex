UI implementation notes

- All mutable state needs to go in the import state or you'd need some kind of <ModalChild> weirdness.
- All derived state should go in the components, e.g. bucket view.
- Preferably have state be generic instead of needing redundant phase.
- Reversible, should not throw away state. State should be decreasingly optional properties instead of discriminated union.

Model state repr notes

- Doing everything lazily and working with untyped PBSRecords is a bad approach. It forces you to duplicate logic in a bunch of places, like between the form class bucketer and the non-bucket extractor. It also requires you to pass around a lot more data and in more awkward shapes than is necessary, and to do extra guards.
- Centralize all logic and transform everything eagerly.
  - Included forms should be a property of Pokemon.

Something like...

pokemons: Pokemon {
  section: string;
  resolved: RawPokemon;

  // Order by subsection.
  forms: PokemonForm {
    subsection: number;
    resolved: RawPokemon;
    bucketIndex: number;
  }[]
}

// Ordered by their [section], not just coincidental inclusion order, sort eagerly on parse.
dexes: Dex {
  section: number;
  pokemonSections: string[];
}[]

Don't use a pool. Keep the same layout we have now, but with PBSPokemon and such instead of PBSRecord.
parsed.pokemons should be a map, and when parsing forms it should append them to the pokemon with that section

Forms shouldn't contain a bucket index because that requires buckets to be eagerly loaded. Instead you could walk buckets, look up pokemon in the map, look up form by index, and add them to a disabled map when extracting.

Error handling flow notes

- Because several steps have their own upload buttons, they all need to display errors.
- The next button is disabled if there are errors. Skip is not, just ignore the errors.
- A step with an empty state should render in its empty state if there are errors, for example the dex picker. Because if you end up pressing remove files with errors it would pull the state you're working on out from under you in the case of a partially valid file.
- The landing page works a bit different since it auto advances on file upload. The button is never disabled, but the handler checks for errors. Uploading files always overwrites, so no remove files with errors button is shown.
- It should be impossible to advance past the landing with zero pokemon (which is a late error). The landing does not have a skip button or a remove files with errors button. So by getting past the landing you at least have one valid pokemon.txt, though anything you upload later may be wholly and partially invalid.
  - Maybe possible if you edit the file while importing, but I'm going to call that unspecified behaviour. And it wouldn't crash or anything, just be confusing.
